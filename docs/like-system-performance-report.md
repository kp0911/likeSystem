# 좋아요 처리 시스템 성능 비교 보고서

## 1. 프로젝트 개요

이 프로젝트는 유튜브와 같은 서비스에서 많은 사용자가 동시에 하나의 영상에 좋아요를 누르는 상황을 가정하고, 좋아요 처리 방식에 따라 응답 성능과 DB 부하가 어떻게 달라지는지 확인하기 위해 만들었다.

핵심 질문은 다음과 같다.

```text
좋아요 요청이 발생할 때마다 DB에 직접 update를 실행하면,
대규모 트래픽 상황에서 DB는 어떻게 버틸 수 있는가?
```

이를 확인하기 위해 같은 기능을 세 가지 방식으로 구현하고 k6로 부하 테스트를 수행했다.

| 구분 | API | 처리 방식 | 핵심 특징 |
| --- | --- | --- | --- |
| 동기 처리 | `/api/v1/like/sync` | DB 비관적 락으로 직접 증가 | 응답 시점에 DB 반영 완료, 고부하에서 row lock 대기 증가 |
| 기존 비동기 처리 | `/api/v1/like/async` | Redis 중복 체크 후 RabbitMQ에 개별 이벤트 발행 | HTTP 요청과 DB 업데이트 분리, 좋아요 1건당 메시지 1개 |
| 버퍼 비동기 처리 | `/api/v1/like/buffered-async` | Redis에 누적 후 주기적으로 delta 이벤트 발행 | 요청 시점에는 Redis만 갱신, DB는 누적값 단위로 일괄 반영 |

## 2. 기술 스택과 구성

| 영역 | 사용 기술 | 역할 |
| --- | --- | --- |
| Application | Java 21, Spring Boot | REST API 및 비즈니스 로직 구현 |
| Database | MariaDB | 최종 좋아요 수 저장 |
| ORM | Spring Data JPA, Hibernate | `Video` 엔티티 저장 및 조회 |

| Message Queue | RabbitMQ | 기존 비동기 이벤트 및 버퍼 비동기 delta 이벤트 전달 |
| Load Test | k6 | 세 가지 API 성능 측정 |
| Runtime | Docker Compose | MariaDB, Redis, RabbitMQ 로컬 실행 |

## 3. 구현 방식

### 3.1 동기 처리

동기 방식은 요청이 들어오면 DB에서 해당 영상 row를 비관적 락으로 조회한 뒤 `like_count`를 즉시 증가시킨다.

```text
Client
  -> /api/v1/like/sync
  -> Spring Boot
  -> MariaDB row lock 획득
  -> like_count + 1
  -> HTTP 200 응답
```

장점은 구조가 단순하고, HTTP 200 응답을 받으면 DB 반영까지 완료되었다고 판단하기 쉽다는 점이다. 단점은 동일한 영상에 요청이 몰릴수록 하나의 DB row에 lock 경합이 발생한다는 점이다.

### 3.2 기존 비동기 처리

기존 비동기 방식은 Redis Set으로 사용자 중복 여부를 확인하고, 새로운 좋아요일 때 RabbitMQ에 개별 `LikeEvent`를 발행한다. Consumer는 메시지를 하나씩 소비하면서 DB의 좋아요 수를 1씩 증가시킨다.

```text
Client
  -> /api/v1/like/async
  -> Redis Set 중복 체크
  -> Redis count + 1
  -> RabbitMQ LikeEvent 발행
  -> HTTP 200 응답

Consumer
  -> LikeEvent 1개 소비
  -> MariaDB like_count + 1
  -> ACK
```

이 방식은 사용자 요청 스레드가 DB 업데이트를 기다리지 않아도 된다는 장점이 있다. 하지만 좋아요가 10,000건 발생하면 RabbitMQ 메시지도 10,000개, DB update도 최종적으로 10,000번 발생한다. 즉, DB 업데이트를 비동기화했지만 DB 업데이트 횟수 자체를 줄이지는 못한다.

### 3.3 버퍼 비동기 처리

버퍼 비동기 방식은 사용자가 좋아요를 누르면 Redis에 먼저 누적한다. 요청 시점에는 RabbitMQ에 메시지를 보내지 않고, 별도 Scheduler가 일정 주기마다 Redis에 쌓인 pending count를 읽어 RabbitMQ에 `LikeCountDeltaEvent`로 전달한다. Consumer는 이 delta만큼 DB를 한 번에 증가시킨다.

```text
Client
  -> /api/v1/like/buffered-async
  -> Redis Set 중복 체크
  -> Redis display count + 1
  -> Redis pending count + 1
  -> HTTP 200 응답

Scheduler
  -> Redis pending count 읽기
  -> pending count 0으로 초기화
  -> RabbitMQ LikeCountDeltaEvent(videoId, delta) 발행

Consumer
  -> LikeCountDeltaEvent 소비
  -> MariaDB like_count += delta
  -> ACK
```

이 방식은 좋아요 10,000건이 짧은 시간에 발생해도 DB update를 10,000번 실행하지 않고, 일정 시간 동안 모인 delta를 기준으로 적은 횟수의 update로 반영할 수 있다.

## 7. 비교 분석

### 7.1 처리량

동기 방식은 초당 약 469건을 처리했고, 기존 비동기 방식은 초당 약 948건을 처리했다. 기존 비동기 방식은 DB update를 요청 경로에서 분리했기 때문에 동기 방식보다 처리량이 약 2.02배 증가했다.

버퍼 비동기 방식은 초당 약 3,676건을 처리했다. 동기 방식 대비 약 7.83배, 기존 비동기 방식 대비 약 3.88배 높은 처리량이다. 이는 요청마다 RabbitMQ 메시지를 발행하지 않고 Redis에 빠르게 누적한 뒤, 별도 flush 작업에서 delta 단위로 처리하기 때문이다.

### 7.2 응답 시간

동기 방식의 평균 응답 시간은 752.69ms였고, 기존 비동기 방식은 321.45ms였다. 기존 비동기 방식은 DB lock 대기를 요청 경로에서 제거해 응답 시간을 줄였다.

버퍼 비동기 방식의 평균 응답 시간은 8.31ms, p95는 14.76ms였다. 이는 요청 시점에서 수행하는 작업이 Redis Set 추가와 Redis counter 증가 정도로 제한되기 때문이다.

### 7.3 DB 부하 관점

세 방식의 가장 큰 차이는 DB update 횟수다.

| 방식 | 요청 10,000건 발생 시 예상 DB update |
| --- | --- |
| 동기 처리 | 10,000번 |
| 기존 비동기 처리 | 최종적으로 10,000번 |
| 버퍼 비동기 처리 | flush 주기와 videoId 수에 따라 소수 번 |

기존 비동기 방식은 HTTP 응답 성능을 개선하지만, DB update 총량은 줄이지 못한다. 반면 버퍼 비동기 방식은 Redis에 좋아요 수를 모아두고 delta 단위로 DB에 반영하므로, 대규모 트래픽에서 DB 부하를 줄이는 목적에 더 잘 맞는다.

### 7.4 안정성

세 방식 모두 실패율은 0.00%, 성공률은 100.00%였다. 즉, 이번 테스트 조건에서는 세 방식 모두 HTTP 요청을 안정적으로 처리했다.

다만 HTTP 성공의 의미는 방식마다 다르다.

| 방식 | HTTP 200의 의미 |
| --- | --- |
| 동기 처리 | DB 반영까지 완료 |
| 기존 비동기 처리 | Redis 처리와 RabbitMQ 개별 이벤트 발행 완료 |
| 버퍼 비동기 처리 | Redis 누적 완료 |

버퍼 비동기 방식에서는 HTTP 200 이후 Scheduler와 Consumer가 최종 DB 반영을 완료해야 한다. 따라서 RabbitMQ `like.aggregate.queue` 상태와 DB 최종 `like_count`를 함께 확인해야 한다.

## 8. 결론

이번 테스트의 핵심 결론은 다음과 같다.

| 관점 | 가장 적합한 방식 | 이유 |
| --- | --- | --- |
| 즉시 DB 반영 | 동기 처리 | HTTP 응답 시점에 DB update 완료 |
| 요청 응답 속도 | 버퍼 비동기 처리 | 요청 경로에서 Redis만 갱신 |
| 대규모 요청 수용 | 버퍼 비동기 처리 | 처리량이 가장 높음 |
| DB update 횟수 감소 | 버퍼 비동기 처리 | Redis 누적값을 delta 단위로 일괄 반영 |
| 구현 단순성 | 동기 처리 | Redis, RabbitMQ, Scheduler 운영 불필요 |
| 최종적 일관성 학습 | 버퍼 비동기 처리 | 즉시 반영 대신 시간이 지나며 DB 값이 수렴 |

프로젝트의 원래 목적은 “좋아요 요청이 발생할 때마다 DB에 직접 update를 실행하지 않고, Redis와 메시지 큐를 활용해 DB 부하를 낮추는 구조를 이해하는 것”이었다. 이 목적에는 기존 비동기 방식보다 버퍼 비동기 방식이 더 적합하다.

정리하면 다음과 같다.

- 동기 방식은 구조가 단순하지만 단일 row에 요청이 집중되면 DB lock 병목이 발생한다.
- 기존 비동기 방식은 HTTP 응답 성능은 개선하지만, 좋아요 1건당 메시지 1개와 DB update 1회가 발생한다.
- 버퍼 비동기 방식은 Redis에 좋아요를 먼저 누적하고, 누적 delta를 RabbitMQ와 Consumer를 통해 DB에 일괄 반영하므로 대규모 트래픽 분산 처리 목적에 가장 부합한다.

## 9. 추가 확인이 필요한 항목

버퍼 비동기 방식은 HTTP 응답 성능만으로 최종 성공 여부를 판단하면 안 된다. 다음 항목을 함께 확인해야 한다.

| 확인 항목 | 확인 방법 | 의미 |
| --- | --- | --- |
| RabbitMQ `like.queue` | RabbitMQ 관리 화면 | 기존 비동기 개별 이벤트 대기 수 |
| RabbitMQ `like.aggregate.queue` | RabbitMQ 관리 화면 | 버퍼 비동기 delta 이벤트 대기 수 |
| Redis pending count | Redis CLI | 아직 RabbitMQ로 flush되지 않은 좋아요 수 |
| DB 최종 반영 수 | MariaDB에서 `video.like_count` 조회 | 최종 좋아요 수 반영 여부 |

DB 최종 값 확인 명령:

```powershell
docker exec -it mariadb-container mariadb -u db_user -pdb_password like_system -e "select id, like_count from video where id = 1;"
```

RabbitMQ의 `Ready` 값이 테스트 종료 후 0으로 내려가고, DB의 `like_count`가 요청 수에 근접하게 반영되면 최종 반영까지 정상적으로 따라잡은 것으로 판단할 수 있다.

## 10. 학습 포인트

- DB 비관적 락은 정합성을 이해하기 쉽지만, 같은 row에 요청이 집중되면 응답 시간이 급격히 증가한다.
- 요청과 DB update를 분리하는 것만으로도 HTTP 응답 성능은 개선된다.
- 하지만 DB update 횟수를 줄이려면 개별 이벤트 방식이 아니라 Redis 누적값을 delta 단위로 반영하는 구조가 필요하다.
- Redis는 중복 좋아요 방지뿐 아니라 사용자에게 즉각적인 좋아요 수 증가를 보여주기 위한 임시 카운터로 사용할 수 있다.
- RabbitMQ는 개별 이벤트 전달에도 사용할 수 있지만, 대규모 트래픽에서는 집계된 delta 이벤트를 전달하는 방식이 DB 보호에 더 효과적이다.
- 버퍼 비동기 구조는 최종적 일관성을 전제로 한다. 즉, 사용자는 빠른 응답을 받고 DB 값은 잠시 뒤 정확한 값으로 수렴한다.
- 부하 테스트 결과는 평균값만 보면 부족하며, p95 같은 꼬리 지연 지표를 함께 봐야 실제 사용자 체감 성능을 판단할 수 있다.
