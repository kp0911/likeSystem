# 좋아요 처리 시스템 성능 비교 보고서

## 1. 프로젝트 개요

이 프로젝트는 동시성 환경에서 영상 좋아요 수를 안정적으로 증가시키는 방법을 비교하기 위해 만든 Spring Boot 기반 예제이다. 같은 `videoId`에 다수의 사용자가 동시에 좋아요 요청을 보낼 때, 데이터 정합성과 응답 성능이 어떻게 달라지는지 확인하는 것이 목적이다.

비교 대상은 두 가지 방식이다.

| 구분 | API | 처리 방식 | 핵심 특징 |
| --- | --- | --- | --- |
| 동기 처리 | `/api/v1/like/sync` | DB 비관적 락으로 직접 증가 | DB 반영이 즉시 일어나지만, 같은 row에 요청이 몰리면 대기 시간이 증가 |
| 비동기 처리 | `/api/v1/like/async` | Redis 중복 체크 후 RabbitMQ 이벤트 발행, Consumer가 DB 반영 | HTTP 응답은 빠르지만, DB 최종 반영은 Consumer 처리 이후 완료 |

## 2. 기술 스택과 구성

| 영역 | 사용 기술 | 역할 |
| --- | --- | --- |
| Application | Java 21, Spring Boot | REST API 및 비즈니스 로직 구현 |
| Database | MariaDB | 영상 좋아요 수 저장 |
| ORM | Spring Data JPA, Hibernate | `Video` 엔티티 저장 및 조회 |
| Cache / Deduplication | Redis | 비동기 좋아요 요청에서 사용자 중복 좋아요 방지 |
| Message Queue | RabbitMQ | 비동기 좋아요 이벤트 전달 |
| Load Test | k6 | 동기/비동기 API 성능 측정 |
| Runtime | Docker Compose | MariaDB, Redis, RabbitMQ 로컬 실행 |

## 3. 구현 방식

### 3.1 동기 좋아요 처리

동기 방식은 요청이 들어오면 DB에서 해당 영상 row를 비관적 락으로 조회한 뒤 `like_count`를 즉시 증가시킨다.

처리 흐름:

```text
Client
  -> /api/v1/like/sync
  -> Spring Boot
  -> MariaDB row lock 획득
  -> like_count 증가
  -> HTTP 200 응답
```

장점은 흐름이 단순하고, 응답이 성공하면 DB 반영도 완료되었다고 판단하기 쉽다는 점이다. 단점은 같은 영상에 요청이 집중되면 하나의 row에 lock 경합이 생겨 응답 시간이 증가한다는 점이다.

### 3.2 비동기 좋아요 처리

비동기 방식은 요청이 들어오면 Redis Set으로 사용자 중복 여부를 확인하고, 새로운 좋아요일 때 RabbitMQ에 이벤트를 발행한다. 실제 DB 증가는 RabbitMQ Consumer가 메시지를 받아 처리한다.

처리 흐름:

```text
Client
  -> /api/v1/like/async
  -> Spring Boot
  -> Redis Set 중복 체크
  -> RabbitMQ 이벤트 발행
  -> HTTP 200 응답

RabbitMQ Consumer
  -> like.queue 메시지 소비
  -> MariaDB like_count 증가
  -> ACK
```

장점은 HTTP 요청 처리 경로에서 DB row lock 대기 시간을 줄일 수 있어 사용자 응답 속도와 요청 수용량이 좋아진다는 점이다. 단점은 HTTP 응답 성공 시점과 DB 최종 반영 완료 시점이 다르므로, RabbitMQ queue와 DB 값을 함께 확인해야 한다는 점이다.

## 7. 비교 분석

### 7.1 처리량

비동기 방식은 초당 약 966건을 처리했고, 동기 방식은 초당 약 452건을 처리했다. 동일한 부하 조건에서 비동기 방식이 약 2.14배 높은 처리량을 보였다.

이는 동기 방식이 DB row lock을 직접 기다리는 반면, 비동기 방식은 Redis 중복 체크와 RabbitMQ 발행 후 빠르게 응답하기 때문이다.

### 7.2 응답 시간

평균 응답 시간은 동기 방식이 785.57ms, 비동기 방식이 313.64ms였다. 비동기 방식은 평균 응답 시간이 약 60.07% 감소했다.

p95 기준으로도 동기 방식은 1.11초, 비동기 방식은 668.24ms였다. 비동기 방식은 상위 5%의 느린 요청에서도 더 낮은 응답 시간을 보였다.

### 7.3 안정성

두 방식 모두 실패율은 0.00%, 성공률은 100.00%였다. 즉, 이번 테스트 조건에서는 두 방식 모두 요청을 안정적으로 처리했다.

다만 안정성의 의미는 다르다. 동기 방식은 HTTP 200 응답 시 DB 반영까지 완료되었다고 볼 수 있다. 반면 비동기 방식은 HTTP 200 응답이 Redis 처리와 RabbitMQ 발행 성공을 의미하며, DB 최종 반영은 Consumer 처리 완료 이후 확인해야 한다.

## 8. 결론

이번 테스트에서는 사용자 응답 속도와 처리량 기준으로 비동기 방식이 더 좋은 결과를 보였다.

| 관점 | 더 적합한 방식 | 이유 |
| --- | --- | --- |
| 사용자 응답 속도 | 비동기 처리 | DB row lock 대기 없이 빠르게 응답 |
| 고부하 요청 수용 | 비동기 처리 | RabbitMQ를 통해 요청을 완충 |
| 즉시 DB 반영 확인 | 동기 처리 | HTTP 200 응답 시점에 DB 반영 완료 |
| 구현 단순성 | 동기 처리 | Redis, RabbitMQ, Consumer 운영이 필요 없음 |
| 운영 관찰 필요성 | 비동기 처리 | queue 적체와 Consumer 처리량 확인 필요 |

포트폴리오 관점에서 이 프로젝트는 단순히 좋아요 API를 만든 것이 아니라, 같은 기능을 동기 방식과 비동기 방식으로 구현하고 실제 부하 테스트를 통해 장단점을 비교했다는 점에 의미가 있다.

정리하면 다음과 같다.

- 동기 방식은 구조가 단순하고 정합성을 이해하기 쉽지만, 단일 row에 요청이 집중되면 DB lock 병목이 발생한다.
- 비동기 방식은 HTTP 응답 성능과 처리량이 우수하지만, 최종 DB 반영 상태를 RabbitMQ와 Consumer 관점에서 함께 확인해야 한다.
- 좋아요처럼 짧은 시간에 요청이 몰릴 수 있고 즉시 최종 DB 반영이 절대적으로 필요하지 않은 기능에는 비동기 구조가 더 적합할 수 있다.

## 9. 추가 확인이 필요한 항목

비동기 테스트 결과를 완전히 판단하려면 HTTP 성능 외에도 다음 항목을 확인해야 한다.

| 확인 항목 | 확인 방법 | 의미 |
| --- | --- | --- |
| RabbitMQ `Ready` | RabbitMQ 관리 화면에서 `like.queue` 확인 | 처리 대기 메시지 수 |
| RabbitMQ `Unacked` | RabbitMQ 관리 화면에서 `like.queue` 확인 | Consumer가 처리 중인 메시지 수 |
| DB 최종 반영 수 | MariaDB에서 `video.like_count` 조회 | 최종 좋아요 수 반영 여부 |

DB 최종 값 확인 명령:

```powershell
docker exec -it mariadb-container mariadb -u db_user -pdb_password like_system -e "select id, like_count from video where id = 1;"
```

RabbitMQ의 `Ready` 값이 테스트 종료 후 0으로 내려가고, DB의 `like_count`가 요청 수에 근접하게 반영되면 비동기 처리도 최종 반영까지 정상적으로 따라잡은 것으로 판단할 수 있다.

## 10. 학습 포인트

- DB 비관적 락은 데이터 정합성을 보장하는 데 직관적이지만, 같은 row에 요청이 집중되면 응답 시간이 증가한다.
- Redis Set을 사용하면 사용자 단위 중복 좋아요를 빠르게 걸러낼 수 있다.
- RabbitMQ를 사용하면 HTTP 요청 처리와 DB 반영 작업을 분리할 수 있다.
- 비동기 구조에서는 API 응답 성능뿐 아니라 queue 적체, Consumer 처리량, DB 최종 반영 상태를 함께 봐야 한다.
- 부하 테스트 결과는 평균값만 보면 부족하며, p95 같은 꼬리 지연 지표를 함께 봐야 실제 사용자 체감 성능을 판단할 수 있다.
