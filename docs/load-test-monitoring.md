# 지속 부하와 순간 버스트 부하 모니터링

## 변경 배경

기존 프로젝트의 k6 스크립트는 최대 500 VU가 1분 동안 증가하고, 3분 동안 반복 요청을 유지한 뒤 감소하는 지속 동시 부하 모델만 제공했다. 이 방식은 DB, Redis, RabbitMQ가 장시간 요청을 처리할 때의 처리량과 지연을 확인하는 데 적합하다.

다만 실제 서비스에는 짧은 시간에 다수 요청이 집중되는 상황도 있다. 기존 대시보드는 일반적인 요청·Redis·RabbitMQ·DB 상태를 표시했지만, 순간 버스트 시나리오를 실행하는 기능과 “현재 결과가 지속 부하인지 버스트인지”를 구분하는 모니터링 정보가 없었다. 따라서 버스트 결과를 해석하거나 두 부하 모델을 비교하기 어려웠다.

## 추가된 부하 모델

| 구분 | k6 executor | 조건 | 확인 목적 |
| --- | --- | --- | --- |
| 지속 동시 부하 | `ramping-vus` 기본 시나리오 | 1분 ramp-up, 3분 500 VU 유지, 1분 ramp-down, 요청 후 0.1초 대기 | 장시간 처리량, 평균 응답 시간, p95, 누적 DB·큐 병목 |
| 순간 버스트 부하 | `per-vu-iterations` | 500 VU가 각각 대기 없이 요청 1회 | 순간 요청 집중 시 오류율, 응답 지연, Redis·Queue 적체 |

버스트는 정확히 같은 밀리초에 모든 요청을 보낸다는 보장은 없지만, k6가 500개 VU를 동시에 시작해 각 VU가 한 번만 요청하도록 구성한다. 따라서 반복 요청과 대기 시간이 포함된 지속 부하와 구분되는 집중 요청 시나리오다.

## 추가 파일과 실행 모드

| 방식 | 지속 부하 스크립트 | 순간 버스트 스크립트 | 대시보드 mode |
| --- | --- | --- | --- |
| DB 직접 반영 | `load-test-sync.js` | `load-test-burst-sync.js` | `sync`, `burst-sync` |
| Redis 버퍼 비동기 | `load-test-buffered-async.js` | `load-test-burst-buffered-async.js` | `buffered-async`, `burst-buffered-async` |

대시보드 URL:

```text
http://localhost:8080/like-test-dashboard.html
```

대시보드의 `지속 동시 부하`와 `순간 버스트 부하` 영역에서 방식별 버튼을 선택한다. 테스트 실행 중에는 현재 부하 모델과 요청 패턴이 표시된다. 버스트는 매우 빨리 끝날 수 있으므로, 완료 뒤에도 `최근 k6 결과` 표에서 결과를 유지해 확인할 수 있다.

## 모니터링 항목

| 화면 항목 | 의미 | 버스트에서 보는 이유 |
| --- | --- | --- |
| 요청 요약 | endpoint별 요청 수, 성공·실패 수, 평균 응답 시간 | 500개 집중 요청의 수용 여부 확인 |
| 시스템 상태 | Redis display/pending, RabbitMQ 대기 메시지, DB like_count | HTTP 200 이후 비동기 적체와 최종 반영을 분리해 확인 |
| 처리 흐름 | Redis 중복 처리, pending, outbox publish, Consumer, DB 반영 단계별 누적값 | 병목이 요청 수신인지, queue 소비인지 확인 |
| 최근 k6 결과 | `http_reqs`, 평균, p95, 실패율, check 성공률 | 짧은 버스트 종료 후에도 성능 결과 확인 |

요청 요약과 처리 흐름은 마지막 초기화 이후 누적값이다. 테스트 유형별 결과를 정확히 비교하려면 대시보드의 `DB/Redis/Queue 초기화`를 실행한 뒤 한 종류의 테스트만 실행해야 한다.

## 권장 비교 절차

1. 대시보드에서 `DB/Redis/Queue 초기화`를 실행한다.
2. `지속 동시 부하`의 sync 또는 buffered 버튼을 실행한다.
3. `최근 k6 결과`, RabbitMQ 대기 메시지, DB 최종값을 기록한다.
4. 다시 초기화한다.
5. 같은 방식의 `순간 버스트 부하` 버튼을 실행한다.
6. 지속 부하와 버스트의 p95, 실패율, Redis pending, RabbitMQ 대기 메시지, DB 최종값을 비교한다.

## 해석 기준

- 지속 부하는 장기 처리량과 시간이 지날수록 누적되는 병목을 평가한다.
- 버스트는 순간적인 요청 집중을 서버가 받아들이는 능력을 평가한다.
- buffered-async는 HTTP 응답이 빠르더라도 Redis pending, RabbitMQ 대기 메시지, DB like_count가 뒤늦게 수렴할 수 있다.
- sync는 HTTP 응답이 DB 반영 완료를 의미하므로 burst에서 p95가 높아지면 DB write 경합이 직접 드러난다.

이 변경으로 프로젝트는 지속 동시 부하뿐 아니라 순간 버스트 부하도 실행하고, 각 결과가 어떤 부하 모델에서 생성됐는지 대시보드에서 구분하며 모니터링할 수 있다.
